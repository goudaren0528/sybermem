# Theme Digest: hooks

## Theme
- hooks

## Why This Theme Matters
Hooks are SyberMem's core automation surface. They are the mechanism that turns SyberMem from "a set of slash commands the user must remember" into "an active project memory that loads at session start and records at session end." Every other capability — lifecycle layer, cross-platform nudge, fast-path update — depends on hooks working reliably from any directory, on any platform.

## What Stabilized
1. **Auto-record on stop**: A Python stop-hook helper (`record_change_on_stop.py`) writes lightweight `change` trail records from workspace file changes. It uses fingerprint dedup, soft-skip for meta-files (CLAUDE.md, AGENTS.md), bounded theme windows for digest cluster detection, and commit-gap detection.
2. **Root resolution**: Hooks resolve the project root by walking up from cwd until they find `.sybermem/` + `.claude/settings.json` or `.sybermem/INDEX.md`. Global launchers in `~/.claude/sybermem/` delegate to project-level scripts.
3. **Plugin-level hooks**: Claude Code plugin declares `SessionStart` and `Stop` hooks in `hooks/hooks.json`, with a polyglot `run-hook.cmd` wrapper that works on Windows (Git Bash) and Unix. The plugin hooks delegate to the same project-level Python scripts.
4. **File classification guard**: After bug-001 (init-project misclassified a missing hook as "custom/kept"), all managed-file classification now requires file-system verification before any action.

## Cross-Phase Evolution
- **phase-002** (Foundation): change-003 introduced the auto-record stop-hook template and project-level `.claude/settings.json` with `SYBERMEM_RECORD_MODE`. This was the first real automation entry point.
- **phase-001** (Distribution): change-005 refreshed project instruction files to auto/remind mode and created the actual project-level hook helper, completing the template→project pipeline.
- **phase-004** (Root resolution): bug-001 exposed that hooks must resolve the project root from subdirectories. Led to the global launcher architecture and the `resolve_sybermem_root()` pattern used everywhere since.
- **phase-009** (Plugin): change-008 added Claude Code plugin packaging with `hooks/hooks.json` declaring SessionStart and Stop hooks. The plugin hooks are thin delegators to the same project-level Python scripts, so both install paths (plugin and script) share behavior.

## Current Reusable Conclusions
- **Hooks must resolve their own project root.** Never assume cwd is the project root. Walk up.
- **Global launchers delegate to project-local scripts.** This keeps hook behavior versionable per-project while install/update only touches one global file.
- **Stop hook writes `change` records only.** `decision`, `requirement`, and `bug` records are always manual via `/sybermem-record`.
- **File classification requires file-system proof.** Never infer a file's state from settings.json references or conversation context.
- **Two hook paths coexist.** Plugin hooks (`hooks/hooks.json`) and project-local hooks (`.claude/settings.json`) share state via `.sybermem/.nudge-state.json` and fingerprint files.

## Open Edges
- Stop hook `update.ps1` / `update.sh` skill lists are still hardcoded to 8 skills; new skills (search, link, theme-digest) are not distributed by the update scripts yet.
- Plugin hooks and project-local hooks can both fire in the same session if the user has both install paths active. Shared `.nudge-state.json` prevents duplicate nudges, but double auto-trail writes have not been tested under that scenario.
- The lifecycle layer's `session_start_context.py` injects a skill catalog, but that catalog is also hardcoded and doesn't auto-discover new skills.
